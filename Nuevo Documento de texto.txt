PROBLEMAS YA DETECTADOS

Debes reproducir, corregir y cubrir con pruebas los siguientes problemas.

1. Dependencias incompatibles del frontend

`npm ci` falla con `ERESOLVE` porque:

- El proyecto usa React 18.
- Next.js 14 requiere React 18.
- `@react-three/fiber@9.6.1` requiere React 19.
- `@react-three/drei@10.7.7` requiere React 19.

Corrige el árbol de dependencias correctamente.

Preferentemente conserva Next.js 14 y React 18 e instala versiones compatibles de React Three Fiber y Drei, salvo que una actualización coordinada completa sea más segura.

La solución final debe permitir:

`npm ci`

sin utilizar:

- `--force`
- `--legacy-peer-deps`

No ocultes el conflicto.

2. Versión incompatible de Node

`camera-controls@3.1.2` requiere Node 22 o superior, pero el Dockerfile utiliza Node 20.

Corrige la dependencia transitiva o actualiza coordinadamente:

- Dockerfile.
- Documentación.
- Configuración de desarrollo.
- CI, si existe.
- `package.json`, incluyendo `engines`.

3. Vulnerabilidades de npm

Se detectaron 12 vulnerabilidades:

- 1 moderada.
- 10 altas.
- 1 crítica.

Ejecuta la auditoría, identifica los paquetes responsables y corrígelos sin romper la aplicación.

No uses `npm audit fix --force` como solución ciega. Si necesitas un cambio mayor, ejecútalo de forma controlada y valida toda la aplicación.

4. Worker de Celery mal configurado

El servicio `worker` de `docker-compose.yml` hereda el comando de Uvicorn y no inicia un worker Celery real.

Configúralo para consumir ambas colas:

`celery -A app.workers.celery_app worker --loglevel=info -Q cv_pipeline,rf_engine`

Añade una comprobación de salud o una verificación funcional equivalente.

5. Los archivos subidos no se guardan realmente

La subida de planos crea un registro `FloorPlanAsset`, pero no almacena el archivo original en MinIO/S3.

Esto genera URLs hacia objetos inexistentes.

Corrige el flujo para que:

- El archivo se valide.
- El nombre se normalice.
- Se almacene realmente en MinIO.
- Se cree el asset.
- Se cree el job.
- El worker reciba una referencia al objeto.
- Exista rollback o limpieza si alguna operación falla.
- La URL firmada permita recuperar el archivo.

6. Archivos demasiado grandes enviados por Celery

Actualmente archivos de hasta 50 MB se convierten a hexadecimal y se envían mediante Redis/Celery, duplicando aproximadamente su tamaño.

Corrige el diseño:

- Guarda primero el archivo en MinIO.
- Envía al worker solo `asset_id`, bucket/key o una referencia pequeña.
- Haz que el worker descargue el archivo.
- No envíes archivos grandes dentro del mensaje Celery.

7. Endpoints de subida duplicados

Existen:

- `/floors/{floor_id}/upload`
- `/floors/{floor_id}/upload-plan`

Unifica la lógica.

Si necesitas conservar ambos por compatibilidad, uno debe actuar como alias de una única implementación compartida, sin duplicación.

8. Fallos graves de autorización multi-tenant

La autenticación no garantiza aislamiento entre organizaciones.

Corrige todos los endpoints relacionados con:

- Floors.
- Geometry.
- APs.
- Jobs.
- Uploads.
- Assets.
- RF.
- Buildings.
- Projects.
- Reports.

Problemas concretos:

- Algunos endpoints verifican autenticación, pero no membresía.
- `get_job` permite buscar trabajos por ID sin comprobar propietario u organización.
- Algunos endpoints anidados no verifican que `org_id`, `project_id`, `building_id` y `floor_id` pertenezcan a la misma jerarquía.
- El reporte no comprueba correctamente la membresía.
- Un usuario podría acceder a recursos de otra organización si conoce sus identificadores.

Implementa autorización centralizada y reutilizable.

Roles:

- Viewer: solo lectura.
- Editor: lectura y edición.
- Admin: administración y operaciones destructivas.

Añade pruebas con dos organizaciones y verifica que el acceso cruzado devuelva 403 o 404 de forma consistente.

9. UUID aleatorio como organización de respaldo
